# Архитектура

## Компоненты

```text
                ┌─────────────── FastAPI (один процесс) ───────────────┐
форма на сайте ─┤ POST /api/v1/runs                                     │
GitHub Issues ──┤ IssuePoller (опрос раз в 60 с)  ─┐                    │
вебхук GitHub ──┤ POST /api/v1/webhooks/github    ─┼→ RunManager ──→ LangGraph ──→ GitHub API
Telegram-кнопки ┤ TelegramPoller (long polling)  ──┘   (фоновые задачи)  │  ↑ ↓      Groq API
сайт: кнопки ───┤ POST /api/v1/runs/{id}/decision                        │  чекпойнты  Telegram
                │ Store (runs.db): статусы, события, данные одобрения    │  (SQLite)   LangSmith
                └────────────────────────────────────────────────────────┘
```

* **Публичный адрес не нужен.** Issues опрашиваются через REST API, нажатия Telegram-кнопок забираются long polling (`getUpdates`). Вебхук GitHub — опция на будущее.
* **Два хранилища.** `checkpoints.db` — состояние графа (LangGraph `AsyncSqliteSaver`, `thread_id` = id запуска). `runs.db` — то, что видит человек: статус, события, данные для одобрения.

## Граф

```text
START → intake → load_repo → reproduce → investigate → confirm_repro ─┬─ баг не подтверждён ──────────→ report → END
                                                                     └─ подтверждён → fix ⇄ commit → verify → reflect
reflect ─┬─ баг ПОДТВЕРЖДЁННО исправлен → review → request_approval → await_approval ─┬─ да ─→ open_pr → post_pr_check → report
         ├─ тесты падают, попытки есть → fix (с логом падения)                          └─ нет ─→ cleanup → report
         └─ попытки кончились / не подтверждено → cleanup → report
```

Без репозитория граф идёт короче: `intake → diagnose → report` — диагноз по тексту ошибки без доступа к коду (см. ниже).

**Главное правило: к человеку (HITL) агент идёт только с подтверждённо исправленным багом.**
Сначала баг воспроизводится фактами, потом исправляется, потом проверяется тем же фактом. Нет воспроизведения — нет исправления и нет PR.

| Узел | Что делает | Модель |
|---|---|---|
| intake | Нормализует репозиторий, разбирает стек-трейс регулярками (без LLM), отбрасывает фреймы библиотек | — |
| diagnose | Только без репозитория. Факты из текста без модели (место выброса исключения, тип, язык, цепочка вызовов) + гипотеза модели в JSON: причина, шаги, пример кода, уверенность, как проверить, чего не хватает. Помечается как непроверенная | main |
| load_repo | Ветка по умолчанию, SHA, дерево файлов (кэш по `repo+sha`), сопоставление фреймов с файлами | — |
| reproduce | Чем подтвердить баг: тесты исходного кода в песочнице (падают → воспроизведено); проходят или тестов нет → агент напишет регрессионный тест; без песочницы — падает ли CI на исходном коммите | — |
| confirm_repro | Если баг ещё не подтверждён — пишет регрессионный тест (до 2 попыток) и требует, чтобы он падал на исходном коде, причём не из-за ошибки в самом тесте. Не вышло или дефект не найден → итог `not_reproduced`, без ветки, PR и HITL | main |
| investigate | ReAct-цикл: `read_file`, `search_code`, `list_files`; завершается вызовом `submit_finding` (Pydantic-схема `Finding`) | main |
| fix | Пишет полную новую версию файла; парсинг ответа, diff, проверка синтаксиса до коммита | main |
| commit | Создаёт ветку `ai-fix/<id>` (один раз) и коммитит файл | — |
| verify | Если баг воспроизведён — тесты коммита агента в песочнице и сравнение с исходным: что починено, нет ли новых падений. Иначе — GitHub Actions по SHA коммита (если в репозитории есть workflow) | — |
| reflect | На ревью — только при `verified` (баг подтверждённо исправлен). Тесты падают → ещё попытка с логом (Reflexion). Иначе — остановка без PR | — |
| review | Security-скан добавленных строк (OWASP) + ревьюер-модель: вердикт и описание PR | fast |
| request_approval | Сохраняет данные для UI, отправляет Telegram-сообщение с кнопками | — |
| await_approval | Только `interrupt()` — граф останавливается до решения человека | — |
| open_pr | Создаёт Pull Request | — |
| post_pr_check | Есть GitHub Actions — ждёт проверки на PR (`pull_request`); нет — тесты коммита PR в песочнице. Итог комментарием в PR | — |
| cleanup | Удаляет ветку при отказе или неудаче | — |
| report | Итог: Telegram, комментарий в issue, результат для UI | — |

Модели (`.env`): main — `openai/gpt-oss-120b`, fast — `openai/gpt-oss-20b`, fallback — `qwen/qwen3.8-27b`. Список моделей Groq меняется (семейство Llama 3.x с аккаунта уже убрано), поэтому названия вынесены в `.env`. Блок рассуждений `<think>…</think>` reasoning-моделей вырезается из ответа.

## Ключевые решения

* **Расследование и исправление — разные вызовы.** Открытые модели ненадёжно совмещают вызовы инструментов с длинным структурированным ответом. Агент с инструментами выдаёт только `Finding`; файл пишет отдельный вызов без инструментов.
* **Исправление — полный файл между маркерами**, а не JSON: большой код в JSON-аргументах модели часто ломают экранированием. Защита от «обрезанного» файла: новая версия не может быть короче 40% исходной.
* **Честная проверка: воспроизвести → исправить → сравнить.** Успех засчитывается, только если тесты, падавшие до исправления, починены и нет новых падений (`compare_runs`). Если до исправления тесты проходили, это прямо говорится: «тесты ошибку не воспроизводили». Ревьюеру запрещено писать о тестах то, чего не было.
* **Песочница — одноразовые Docker-контейнеры** через Docker Engine API (сокет). Шаг 1 — установка зависимостей (pip / npm с `--ignore-scripts` / go mod, с сетью). Шаг 2 — тесты **без сети**, read-only корневая ФС, без capabilities, `no-new-privileges`, лимиты 768 МБ / 1 CPU / 256 процессов, таймаут. Секретов сервиса в контейнере нет, сокета Docker тоже. Проверено «вредным» тестом: сеть заблокирована, запись в систему запрещена, секретов нет. Прогон ≈8 с. Цена: доступ сервиса к сокету Docker равен root на хосте — поэтому порт открыт только на localhost.
* **GitHub Actions — второй, независимый контур:** используется, если песочница выключена или недоступна, и для проверки после PR, если в репозитории есть workflow. Если нет ни того, ни другого, агент сразу честно пишет «тесты не запускались», без ожидания.
* **Human-in-the-Loop через `interrupt`.** Пауза может длиться часы: состояние в SQLite, процесс можно перезапустить. Побочные эффекты (Telegram) — в отдельном узле до паузы, иначе при возобновлении сообщение ушло бы повторно.
* **Канал одобрения выбирается при старте запуска:** указан chat ID или `@username` и настроен бот → Telegram, иначе сайт. Если отправка в Telegram не удалась, запуск переключается на сайт.
* **Chat ID бот находит сам:** человек пишет боту `/start`, бот сохраняет чат и username (таблица `telegram_chats`) и отвечает его chat ID. В форме достаточно `@username`. Для запусков из issue берётся `TELEGRAM_DEFAULT_CHAT_ID`, а если он пуст — последний чат, написавший `/start`. Принимаются только личные чаты.
* **Fallback-механизмы:** повторы GitHub API (429/5xx/сеть, `Retry-After`), запасная модель при ошибке основной (`tool_use_failed`, лимиты), ошибки инструментов возвращаются агенту текстом, после исчерпания итераций — файл из стек-трейса, при сбое запуска — удаление ветки и уведомление.
* **Оптимизация контекста:** дерево — не больше 300 путей в промпте, `read_file` с диапазоном строк и лимитом 400 строк, кэш файлов в рамках расследования, кэш дерева между запусками, текст ошибки обрезается до 6000 символов.
* **Восстановление после рестарта:** запуски в статусе `running` продолжаются с последнего чекпойнта.

## Где лежит код: GitHub или локальная папка

`RepoRouter` направляет вызовы по имени репозитория: `local:<папка>` → `LocalRepoClient` (git в папке, подключённой в контейнер как `/projects`), остальное → `GitHubClient`. Интерфейс одинаковый, граф агента не знает, откуда код. В локальном режиме CI нет (проверка только в песочнице), «Pull Request» — ветка `ai-fix/...`, собранная без изменения рабочих файлов (`hash-object` → временный индекс → `commit-tree` → `update-ref`), описание — в git notes.

## Языки (`app/languages.py`)

Логика агента от языка не зависит; профиль языка (`TestPlan`) задаёт только образ, команды и разбор вывода.

| Язык | Определение | Образ | Установка (с сетью) | Тесты (без сети) | Разбор |
|---|---|---|---|---|---|
| Python | файлы стек-трейса, `requirements.txt`/`pyproject.toml`, `.py` | `python:3.12-slim` | `pip install --target` | `pytest -rfE` | строки `FAILED`/`ERROR` |
| JS/TS | `package.json` | `node:22-slim` | `npm ci --ignore-scripts` | Jest/Vitest с JSON-отчётом, `node --test` с TAP | JSON-отчёт / TAP |
| Go | `go.mod` | `golang:1.23-alpine` | `go mod download` | `go test -json ./...` (`GOPROXY=off`) | JSON-события |

Идентификатор теста — `<файл или пакет>::<имя>`, поэтому сравнение «до/после» (`compare_runs`) общее. Падение до запуска тестов (`::(build)`, `::(suite)`, ошибка сбора) на исходном коде не считается воспроизведением бага — это проблема окружения. Регрессионный тест кладётся туда, где его найдёт раннер: `tests/test_ai_regression_*.py`, рядом с существующими `*.test.js`/`*.spec.ts`, в каталог пакета `*_test.go`. Образы скачиваются при первом запуске на соответствующем языке.

## Наблюдаемость

* **LangSmith:** `LANGSMITH_TRACING=true` и ключ в `.env`. Каждый запуск — трейс `bug-investigation` с `metadata.run_id`; видны узлы, вызовы моделей и инструментов, токены.
* **UI:** лента событий узлов («Агент читает app/cart.py», «Попытка 2/3…»), счётчик токенов.
* **Логи контейнера:** `make logs`.

## Ограничения прототипа

* Падающие тесты на исходном коде считаются воспроизведением жалобы, даже если они ловят другой баг; человек видит причину и diff в карточке одобрения.

* Исправляется один файл за запуск.
* Песочница поддерживает Python (pytest), JavaScript/TypeScript (Jest, Vitest, node --test; иначе `npm test` только по коду возврата) и Go (go test). Для остальных языков проверка — через GitHub Actions; без CI исправление не предлагается.
* Сравнение «до/после» по отдельным тестам есть только в песочнице; через GitHub Actions баг засчитывается исправленным, только если CI падал на исходном коммите и прошёл на коммите агента.
* Нет аутентификации на сайте (порт открыт только на localhost).
* Фоновые задачи живут в процессе FastAPI; для нагрузки нужен отдельный воркер (Celery/arq).
